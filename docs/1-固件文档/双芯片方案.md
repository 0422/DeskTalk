# ESP32-S3 + ESP32-C6 双芯片架构分析

本文档分析双芯片方案的底层架构差异、工程分工基础和设计决策。

**注意**：当前项目（V2/V3）暂未实施双芯片方案，本文档作为未来技术路线参考。

---

## 芯片分工基础

### ESP32-S3（决策节点）

- **Xtensa LX7 双核**，支持 ESP-NN SIMD 指令
- TFLite Micro 量化模型性能：ESP-NN SIMD 路径比标量 C 实现快约 **4 倍**
- DS-CNN 关键词识别：100KB INT8 模型、96% 准确率、单次推理约 **54ms**
- 更丰富的 I²S 通道和 USB OTG，适合音频采集与调试
- **角色**：AFE 音频前处理、本地唤醒词、轻量 AI 推理、I2S 音频输出

### ESP32-C6（通信节点）

- **RISC-V 核心** + Wi-Fi 6 + 802.15.4 多协议射频
- Wi-Fi 6 支持 OFDMA 和 TWT（目标唤醒时间），在拥挤 2.4GHz 频段下信道效率显著优于 Wi-Fi 4
- 深度睡眠功耗可低至 **微安级**，远低于 S3 的睡眠电流
- 独有的 802.15.4 射频为 Thread/Zigbee 提供原生支持
- **角色**：Wi-Fi 连接与协议栈、低功耗后台任务、可选 802.15.4 网关

## 通信链路：UART vs SPI vs SDIO

### 当前选择：UART 全双工

**优势**：
- 引脚需求极简（仅 TX/RX，可选流控），适合磁吸接口等机械约束严格的场景
- 控制指令帧长通常 ≤32 字节，115200 波特率下传输延迟约 **2.8ms**
- 协议实现简单，无需处理 SPI 时钟同步或 SDIO 复杂初始化时序

**瓶颈**：
- 115200bps ≈ 11.5KB/s
- 16kHz 16bit 单声道 PCM 原始数据是 32KB/s
- Opus 压缩后约 2–4KB/s
- **适用场景**：S3 做 TTS 后经 C6 上传云端（勉强够用）
- **不适用场景**：S3 采集音频经 C6 流式上传（会成为瓶颈）

**建议**：波特率直接上 **460800** 以上，只传文本 JSON 时余量充足。

### 可选替代：SPI / SDIO

- **SDIO**：最高吞吐，但需要 6 根信号线 + 上拉电阻，磁吸接口可能无法承受
- **SPI**：全双工需 4-5 根线，可考虑的折中方案
- ESP-Hosted 组件明确支持 SDIO 和 SPI 作为主机-协处理器链路

## ESP-SR / MultiNet 能力边界

- 支持最多 **300 条自定义中英文命令**，可动态增删，无需重新训练模型
- AFE（音频前端）提供噪声抑制、VAD 和回声消除
- **场景定位**：90% 的高频交互可以用 **<50 条命令覆盖**，关键在于命令集设计质量

**拓展方向**：声纹识别辅助命令路由——识别"是谁在说话"后，为不同用户配置不同命令映射，在不增加模型复杂度的前提下扩展交互维度。

---

## 本地 TTS 可行性

sanoTTS 项目实测：**$3 的 ESP32-S3** 上，294K 参数的 int8 模型（337KB）实现了 RTF 0.383，即合成速度比实时快 **2.6 倍**。

**结论**：
- S3 完全可以在本地运行实时 TTS，无需 C6 参与
- S3 可直接驱动 I²S DAC 输出音频，C6 角色退化为"可选上行通道"
- 本地 ASR + TTS 可实现**完全离线语音交互闭环**：唤醒 → 命令识别 → 本地逻辑 → TTS 反馈

## 开发环境选择

**ESP-IDF 是唯一能在双芯片上提供完整功能支持的框架**。

### Arduino 的两大硬伤

1. **C6 的 802.15.4 在 Arduino 上不可用**：
   - Thread 和 Zigbee 需要 ESP-IDF v5.x 及专项 SDK 配置
   - Arduino 只支持 Wi-Fi/蓝牙层面，射频底层功能被阉割

2. **S3 的语音功能在 Arduino-as-component 下存在实测失败案例**：
   - ESP32-S3 离线语音识别在 Arduino IDE 独立环境下可工作
   - 但切换到 VSCode ESP-IDF 扩展 + Arduino-as-a-component 模式后，唤醒词可能失效
   - 这不是配置问题，而是框架层次叠加后引入的兼容性风险

### ESP-IDF 在双芯片方案中的必要性

- **S3 侧**：GMF AI Audio 组件（AFE + WakeNet + 命令词检测）仅以 ESP-IDF 组件形式提供
- **C6 侧**：Wi-Fi 6 的 TWT 和 OFDMA 配置需要在 ESP-IDF 底层访问
- **UART 通信**：ESP-IDF 原生驱动支持 DMA、环形缓冲、事件队列，可分配明确 FreeRTOS 优先级

## 系统设计

### 通信协议：双通道语义

| 通道 | 用途 | 典型帧长 | 可靠性要求 |
|------|------|---------|----------|
| 控制通道 | 指令下发、状态同步、心跳 | ≤32B | 高，需 ACK/重传 |
| 数据通道 | 文本、JSON、传感器聚合 | 可变，分片 | 中，可容忍偶发丢包 |

**帧格式**：帧头（2B magic）+ 长度（2B）+ 类型（1B）+ 载荷 + CRC16

### 电源管理策略

- S3 和 C6 **独立电源域**：各自 LDO/DC-DC 使能控制
- S3 空闲时 Light Sleep，C6 维持 Wi-Fi 连接
- 完全离线时 C6 Deep Sleep，S3 独立运行 ASR/TTS
- C6 的 TWT 特性：只在约定时间窗口醒来接收 AP 数据，其余时间断电射频

### 场景适配

| 场景 | S3 职责 | C6 职责 | UART 流量 |
|------|---------|---------|---------|
| **A：完全离线** | ASR + TTS + 逻辑 | Deep Sleep / BLE 配网 | 仅"需要联网"的文本请求 |
| **B：在线优先** | 唤醒词 + VAD | Wi-Fi + 音频流上传 | I2S PCM 流（需评估 SPI） |
| **C：混合模式**（推荐） | 离线 ASR/TTS 闭环 | OTA、远程控制、云端 LLM | 复杂请求的文本 JSON |

**推荐场景 C**：
- 默认离线闭环（S3 本地 ASR/TTS）
- 复杂请求（如"帮我订机票"）时，S3 将识别文本经 C6 上传云端
- C6 同时负责 OTA 更新、远程控制等后台任务

## 拓展设计方向

1. **边缘-云协同智能降级**：根据网络质量动态选择处理路径，断网时自动切换本地命令识别模式
2. **多协议射频价值挖掘**：C6 的 802.15.4 可作为独立 Thread/Zigbee 网关节点
3. **模型热插拔**：ASR/TTS 模型放在独立 Flash 分区，运行时通过 `esp_partition_mmap` 加载，支持 OTA 分发
4. **GPIO 相位标记**：双芯片跨芯片时间对齐，用逻辑分析仪抓取标记信号测量 UART 传输延迟
