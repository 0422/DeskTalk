## 项目概述

### 目标与结论

本轮目标是验证 ESP32-S3 板端直连 ASR/LLM/TTS 三条云链路的可行性，并降低听感延迟。

**实测结论**：
- 板端直连 `AUDIO_UPLOAD_DONE → PLAYBACK_START` 样本约为 **2.1–2.7 秒**，最好约 **2.1 秒**，未稳定达到 1.5 秒
- TTS WebSocket 建连约 **0.62–0.73 秒** 是最大固定开销
- LLM 首字节约 **0.72–1.15 秒**，含 TLS 握手
- 火山 V3 双向连接复用逻辑已实现，但因内存保护被主动释放，**未真正启用**
- 本地网关方案因部署复杂性和超时问题，**回退到板端直连**

### 延迟基线事件

| 事件 | 记录时机 |
|------|---------|
| `VAD_START` | 本地音频块首次超过阈值 |
| `AUDIO_UPLOAD_DONE` | ASR 最后一块音频发送成功 |
| `ASR_FINAL` | 收到 ASR 最终文本 |
| `LLM_FIRST_BYTE` | 收到 DeepSeek 首个 SSE 增量 |
| `LLM_DONE` | 完整答案解析完成 |
| `TTS_CONNECTED` | TTS WebSocket 建连完成 |
| `TTS_REQUEST_SENT` | TTS 请求帧发送成功 |
| `TTS_FIRST_AUDIO` | 首个 PCM 进入播放队列 |
| `PLAYBACK_START` | 首个 PCM 提交到 I2S DMA |

**典型耗时**：
- `LLM_FIRST_BYTE`：0.72–1.15 秒
- `TTS_CONNECTED`：0.62–0.73 秒
- `TTS_REQUEST_SENT → TTS_FIRST_AUDIO`：0.23–0.62 秒

## 代码结构与迁移

### 开发环境

- **目标硬件**：ESP32-S3-N16R8（16 MB Flash + 8 MB Octal PSRAM）
- **开发环境**：Windows + VS Code ESP-IDF 扩展
- **框架版本**：ESP-IDF v5.3.5
- **串口监视**：`idf.py -p COM4 monitor`
- **构建烧录**：`idf.py build` → `idf.py -p COM4 app-flash monitor`

### 组件版本

| 组件 | 版本 | 说明 |
|------|------|------|
| ESP-IDF | v5.3.5 | 固定范围 `>=5.3,<5.4` |
| ESP-SR | 2.5.4 | 语音识别（解析到 esp-dl 3.3.11） |
| esp_websocket_client | 1.8.0 | ASR/TTS WebSocket |
| led_strip | 2.5.5 | WS2812 LED 驱动 |

### Flash 分区

| 分区 | 大小 | 用途 |
|------|------|------|
| factory | 6 MB | 主应用（原两个 3MB OTA 槽合并） |
| spiffs | ~6.75 MB | 对话历史、舵机参数 |
| model | 3 MB | WakeNet + MultiNet 模型 |
| nvs | 24 KB | Wi-Fi 配置 |
| ota_data | 8 KB | OTA 数据 |

### 资源配置与优化

#### PSRAM 与内部 RAM

- **最初问题**：仅把大对象放入 PSRAM，仍因 Wi-Fi、TLS、WebSocket 和任务栈争用连续内部 RAM 而创建任务失败
- **解决方案**：
  - 将会话、ESP-SR、TTS worker、命令控制台等长生命周期任务栈移入 PSRAM
  - 启用 Wi-Fi/LwIP 优先使用 PSRAM
  - 启用 mbedTLS 外部内存和动态缓冲
  - 采用低内存 Wi-Fi buffer 配置

#### 分配阈值调整

- `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`：4096 → **1024**
  - 原因：4 KB WebSocket 缓冲继续占用内部 RAM，导致 ASR 与常驻 TTS 同时运行时 `Error create websocket task`
  - 保留 64 KB 内部 DMA/关键分配池

#### WebSocket 握手缓冲

- 火山引擎 HTTP Upgrade 响应超过默认 1 KB
- 将传输握手缓冲设为 **4096**，并启用动态缓冲
- 握手完成后释放内存

#### 密钥配置

- 云服务凭据通过项目私有配置头提供
- 不写入迁移文档或串口诊断
- 失败日志只记录状态、响应类型和限长正文

### 稳定性问题修复

#### 缓存断言问题

**问题 1**：唤醒后释放 ESP-SR 时，在 PSRAM 栈任务中执行 `esp_srmodel_deinit()` 触发 Flash/PSRAM cache freeze 断言

**解决方案**：
- 会话期间释放 AFE、WakeNet、MultiNet 和相关任务
- 保持模型分区映射常驻，下一次恢复唤醒时复用映射
- 停用会报告"命令未初始化"的重复命令清理调用

**问题 2**：从 PSRAM 会话栈直接读取 SPIFFS 历史时，Flash cache 禁用期间触发栈完整性断言

**解决方案**：
- 增加使用 4096 字节静态内部 DRAM 栈的同步存储 worker
- 所有 SPIFFS/NVS 初始化、读写和擦除操作统一派发到该任务执行

#### 其他稳定性问题

- **内存不足**：ASR 与常驻 TTS 并行时因连续内部 RAM 不足导致 WebSocket 任务创建失败 → 调整 PSRAM 阈值、任务栈、Wi-Fi/TLS/WebSocket 内存后解决
- **空白回答**：DeepSeek JSON mode 偶发只返回 7～13 字节空白内容 → 改为纯文本流式回复，最多重试一次

### 迁移范围

| 模块 | 迁移内容 |
|------|---------|
| 工程与启动 | ESP-IDF CMake 工程、组件依赖、自定义分区表、分阶段初始化 |

**注意**：摄像头和手势传感器在当前硬件配置中明确保持禁用。

## 功能实现与测试

### 已完成的板端优化

#### VAD 句尾等待

- 900ms → 650ms → **500ms**，减少固定等待
- ⚠️ 500ms 可能导致短暂停顿被误判为结束，需验证 ASR 截断率

#### 延迟打点

- 9 个阶段统一时间戳
- 延迟到 TTS 播放完成后输出，避免阻塞关键路径

#### DeepSeek 流式与上下文压缩

- SSE 增量接收，关闭思考模式
- `max_tokens=80`，answer-only JSON
- 上下文压缩到最近 2 轮，减少请求体

#### TTS 播放队列

- 独立 FreeRTOS 任务 + 有界 PCM 队列
- V3 双向 Session + 明确 `SessionFinished` 完成判断
- I2S 写入失败传播，DMA 排空后静音

### TTS 连接复用尝试

**实现**：唤醒后建立火山 V3 双向连接，每轮新建 Session，物理 WebSocket 复用。

**结果**：启动时成功，但首次唤醒后因内存保护被释放：

```text
TTS reuse before cloud request: heap=55596, largest=44020
TTS persistent connection released before cloud request because internal heap is low
```

**原因**：内部空闲堆 55 KiB、最大连续块 44 KiB，低于保护阈值（96 KiB / 48 KiB），为保证 ASR/LLM 握手成功，主动释放常驻 TTS。

### 板载 TLS 内存限制

| 连接 | 约占用内部 RAM |
|------|--------------|
| ASR WebSocket | ~45 KB |
| DeepSeek HTTPS | ~45 KB |
| TTS WebSocket | ~45 KB |

**关键结论**：
- TLS 上下文必须占用内部 RAM，PSRAM 无法完全替代
- 三连接不能同时常驻，当前顺序执行
- 20 轮测试（见下文）未发现持续内存泄漏，连接关闭后内存基本归还

### 网关方案尝试

**设计**：服务器侧完成 DeepSeek SSE + TTS 合成，ESP32 通过单一网关 WebSocket 接收文本和 PCM。

**结果**：本机测试出现超时，`LLM_FIRST_BYTE` 约 11 秒，体验劣于直连。

**原因**：网关启动时机、地址可达性、超时回退策略叠加，非算力不足。

**当前状态**：网关未移植到 V2 工程（仅 V1 Arduino 工程有实现），当前为板端直连。

## 细节优化

### HTTPS 长连接与双 TLS 危机

**现状**：LLM 每轮从零建连；TTS 长连接逻辑已实现但未真正启用（见上文 §TTS 连接复用尝试）。

- `llm_client.cpp:452` 起，每轮 `chat()` 都执行 `init → perform → cleanup`
- 配置未设置 `keep_alive_enable`，默认为 `false`
- 每轮 LLM 首内容 = DNS + TCP 握手 + mbedTLS 握手 + 请求发送 + 模型 TTFT
- 国内 API、RTT 20~50ms 时，握手固定开销常见 **0.3~1 s**

**双 TLS 并存的内存水位**：

| 字段 | 值 | 含义 |
|------|-----|------|
| internal | 31523 B（≈30.8 KB） | 当前内部 RAM 余量 |
| internal_min | 71 B | 启动至今最低水位 |
| internal_max | 15872 B | 最大连续块仅 15 KB |

**失败一次的代价**：
1. `tts.finish_turn()` 排空当前 TTS 轮
2. `tts.release_persistent_connection()` 拆掉 TTS WSS
3. 若尚未播出任何音频，`llm.chat()` 完整重来（0.5~2 s 量级）
4. 若已有部分播报则宁可失败也不重放

**修改方向**（待拍板）：

| # | 方向 | 预期收益 | 风险/代价 |
|---|------|---------|----------|
| 1 | LLM HTTPS 改长连接 | 每轮省 0.3~1 s | 常驻连接占内存 |
| 2 | TLS session ticket | 重连握手缩短 | 需验证服务端兼容性 |
| 3 | 静音阈值 500→300 ms | 固定省约 200 ms | 短停顿误切 |
| 4 | 换快档 LLM | TTFT 与解码速度 | 接口字段差异 |
