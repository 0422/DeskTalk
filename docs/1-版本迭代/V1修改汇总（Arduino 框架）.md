# 修改汇总
### 模块开关

原程序只有手势传感器能把 start_chat 设置为 true，现在改为了通过唤醒词开启对话。
> 未买入手势追踪模块，将程序中的手势触发停用了，可以通过宏打开。
> 且为方便各模块测试，对麦克风、摄像头、功放、手势追踪等均加了开关，
> 以及某个模块未插到开发板上时，启动时会跳过其初始化环节。

### 离线唤醒词
唤醒识别完全在 ESP32-S3 本地完成，但唤醒后的 ASR、LLM、TTS 仍走现有云端流程。
> 当前流程是半双工的“先听、再回答”，不需要回声消除。
> 若后续要求在机器人说话时也能用语音打断，则需要增加播放中录音、声学回声消除和新的对话状态机。

Arduino ESP32 3.0.0 自带的 WakeNet 模型固定选择 `hi esp`，不能只修改日志文字就变成自定义唤醒词。
改为使用 ESP-SR 自带的英文 MultiNet 命令检测，并把默认的 Hi ESP短语和新增的唤醒词短语注册为同一个命令。
>  MultiNet 自定义命令不是专门训练的 WakeNet 模型，短语识别效果和抗误唤醒能力可能与 ESP-SR 固定 的WakeNet 模型 不同。

增加本地唤醒词 `Hi ESP` 和 `Hi Della`，唤醒后进入最长 10 分钟的连续对话窗口，避免每一轮对话都要重新唤醒。
> 唤醒后，主程序会暂停本地 MultiNet，避免它和云端 ASR 同时读取同一个 I2S 麦克风；
> 云端 ASR 结束后再恢复 MultiNet。
> 恢复时会清空待处理事件，并加入短暂冷却时间，避免上一段语音残留导致重复唤醒。

### DeepSeek直连与多轮对话

- LLM 从第三方中转站迁移到 DeepSeek 官方 `https://api.deepseek.com/chat/completions`，使用 `deepseek-flash` 模型，减少中转服务不可达导致的连接失败。
- 请求使用非流式 JSON 输出、关闭思考模式并限制最大输出长度；回复从 `choices[0].message.content` 中解析。
- 对网络传输错误、HTTP 408、429 和 5xx 响应增加最多 3 次重试。
- ESP32-S3 在 SPIFFS 的 `/chat_history.json` 中保存上下文，每次请求携带系统提示词、历史用户/助手消息及本轮问题，实现多轮对话。
- 历史记录最多保留 10 轮、限制为 16 KiB；无效、不完整或过大的历史文件会自动重置。
- DeepSeek密钥改由被 Git 忽略的 `secrets.h` 提供，并增加 `secrets.example.h`，不再把旧中转站密钥写在业务源码中。

### TTS长回复与音频播放

- TTS WebSocket回调只复制并排队 PCM，由独立 FreeRTOS任务执行阻塞式 I2S播放，防止播放过程阻塞后续网络收包。
- 有 PSRAM 时使用 48 个 PCM队列槽，无 PSRAM 时使用 8 个；队列分片使用独立内存，播放后及时释放。
- 将长回复按完整句子拆为不超过约 120 个 UTF-8字节的小段并逐段合成，切分时不破坏中文字符，避免服务端只生成长文本前半部分。
- 服务端在收到 PCM 后正常关闭连接时按流结束处理，并在播放队列完全排空后结束，不再把正常关闭误判为失败。
- 多段播放期间保持 MAX98357功放开启；整条回复结束后等待 I2S DMA 中最多约 512 ms 的剩余音频播放完再静音，修复段尾吞字。
- 修正成功收到 PCM 时仍输出 `returned no PCM audio` 的错误判断，并记录每段文本长度、PCM字节数和待播放分片数。

### 动作数量与舵机稳定性

- 删除 TTS 播放期间每 3 秒触发的随机语音动作，避免动作任务频繁打断音频和网络处理。
- 提示词将每次回复动作减少为 2～3 个，执行端再硬限制最多执行 3 个动作。
- 空闲随机行为不再自动驱动左右舵机，只保留不会抢占头部控制权的表情行为，降低底部舵机长时间通电后连续旋转的概率。
- 对话期间暂停人脸跟随，完成 ASR、LLM、动作和 TTS 后再恢复，避免多个功能同时控制头部舵机。

### Wi-Fi连接与配网

- Wi-Fi凭据优先保存到 NVS，并保留 SPIFFS配置文件作为旧版本迁移和兼容备份；断线后在主循环中非阻塞重连。
- 配网模式明确使用 `WIFI_AP_STA`，使 `Desk-Emoji` 配网热点和附近网络扫描能够同时工作。
- 检查 SoftAP启动结果及 `192.168.4.1` 地址；扫描失败时清理状态并自动重试一次，不再把扫描错误显示成“未找到网络”。
- 扫描接口增加错误码日志和合法 JSON转义，网页能显示真实扫描失败原因。
- 默认联网目标改为开放网络 `Longemont`，密码为空；启动连接、断线重连和 NVS保存均支持无密码 Wi-Fi。

### 串口日志与诊断

- `Bot:` 回复改为直接输出完整 `String`，绕过原日志器 256 字节格式化缓冲区，解决中文 JSON 在串口中只显示前半段并以乱码字符结尾的问题。
- Wi-Fi日志增加 SSID、连接状态名称、SoftAP地址和扫描结果；ASR、TTS日志增加连接尝试、超时、PCM接收量及播放完成状态，方便区分公网故障、服务端断开与本地播放问题。

对 ASR WebSocket 增加连接重试、超时和连接状态日志，能够区分 Wi-Fi 断开与云端 TLS/WebSocket 握手失败。

2. 按文档第 4 条建议，留一个 GPIO 做相位标记，逻辑分析仪（或第二块板子）抓取，这样迁移后能做新旧对比。

## 优化音频流控和流水线
流式输出+首句触发 TTS

**端云分工**：ESP32-S3 只负责唤醒、音频采集/播放和硬件控制，真正的 ASR、LLM、TTS 全在云端。所以 ESP32-S3 的算力并不是自由对话延迟的瓶颈。

真正的优化发生在云端链路。有用户反馈更新到某个版本后“对话变得几乎 0 延迟”，这说明虾哥在服务端对音频流控和流水线做了大量优化。比如让 LLM 流式输出，生成第一句话就立刻触发 TTS，不用等全文生成。

## 传输协议的选择

- **MQTT+UDP**：音频延迟 **30–50ms**，极低，但弱网下容易丢包爆音。
- **WebSocket**：音频延迟 **100–200ms**，中等，但稳定不丢包。

如果你追求极限低延迟，可以关注一下传输协议的选择。

一次自由对话的端到端延迟，可以拆解为这几段（部分环节可并行）

| 环节          | 典型耗时       | 说明                            |
|-------------|------------|-------------------------------|
| VAD 静默等待    | 500–1000ms | 你停下说话后，系统需等待静默时间确认你“说完了”      |
| ASR 语音识别    | 500–2000ms | 把整段语音转成文字，与语音长度强相关            |
| LLM 首 Token | 700–3000ms | 大模型生成第一个有意义的 token，受模型和算力影响最大 |
| TTS 首包合成    | 300–1000ms | 把文字合成为第一段音频                   |
| 网络传输        | 10–100ms   | Wi-Fi 环境下通常不是主因               |
实测参考：有开发者拆解过虾哥项目的延迟，ASR 约 500ms、VAD 约 600ms、LLM 首 token 约 700ms、TTS 约 300ms，加起来接近 2 秒。另一项测试显示，如果整个链路跑得好，自由对话的端到端延迟可以压到 200–350ms，但这依赖 WebRTC 和良好的网络环境。
