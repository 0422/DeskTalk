# V2：板端直连与网关解决板载资源限制的尝试

## 目标与结论

本轮目标是降低“用户说完话 → 机器人开始播放 TTS”的听感延迟，同时确认 ESP32-S3 板端直连是否能够稳定承载 ASR、DeepSeek LLM、火山 TTS 三条云端链路。

结论如下：

- 板端直连经过 VAD、提示词、SSE、播放队列和错误处理优化后，`AUDIO_UPLOAD_DONE → PLAYBACK_START` 的实际样本大多约为 **2.1–2.7 秒**，较好样本约 **2.1 秒**，仍不能稳定达到 1.5 秒。
- 目前最大的固定耗时仍是 TTS WebSocket 建连，通常约 **0.62–0.73 秒**；建连后请求发送约 **0.01 秒**，首个 PCM 通常还需 **0.23–0.62 秒**。
- 虽然实现了火山 V3 双向连接预热和跨轮复用，但实测时 ESP32-S3 内部堆只剩约 `55 KiB`，最大连续块约 `44 KiB`，低于 TLS 并发保护阈值，因此常驻 TTS 连接在 ASR 开始前被主动释放，连接复用没有真正参与这些测试。
- 本地网关可以把 DeepSeek SSE、TTS 合成和连接复用放到电脑或服务器上，但需要额外部署、鉴权和网络可达性。第一次实测出现网关连接超时，反而增加了约 10 秒级等待，因此当前恢复为板端直连，网关代码保留为可选方案。
- 单纯把 Arduino 框架迁移到 ESP-IDF 不会自动把 2.5 秒降到 1 秒；只有同时改善 TLS 内存布局、长连接和云端流水线，才有机会稳定进入约 1.5–2.0 秒。

## 延迟基线

板端使用 `latency_trace` 记录以下事件：

|事件|记录时机|
|---|---|
|`VAD_START`|本地音频块首次超过当前 VAD 阈值|
|`AUDIO_UPLOAD_DONE`|ASR WebSocket 最后一块音频发送成功|
|`ASR_FINAL`|收到云端 ASR 最终文本|
|`LLM_FIRST_BYTE`|收到 DeepSeek 第一个非空 SSE 增量|
|`LLM_DONE`|完整答案对象解析完成|
|`TTS_CONNECTED`|火山 TTS WebSocket 建连完成|
|`TTS_REQUEST_SENT`|TTS 请求帧发送成功|
|`TTS_FIRST_AUDIO`|第一个 PCM 帧收到并进入播放队列|
|`PLAYBACK_START`|第一个 PCM 块提交给 MAX98357 的 I2S DMA|

近期板端直连样本的说完后延迟如下。这里优先使用 `AUDIO_UPLOAD_DONE → PLAYBACK_START`，因为 `VAD_START` 还包含用户实际说话时长。

|会话|`AUDIO_UPLOAD_DONE → PLAYBACK_START`|
|---|---|
|1|约 2.12 秒|
|2|约 3.01 秒|
|3|约 2.40 秒|
|4|约 2.60 秒|
|6|约 2.70 秒|
|7|约 2.32 秒|

同一批日志中，`LLM_FIRST_BYTE` 通常约 **0.72–1.15 秒**，`LLM_DONE` 在首字节后约 **0.10–0.59 秒**，TTS 建连约 **0.62–0.73 秒**，首 PCM 在请求发送后约 **0.23–0.62 秒**。因此当前直连链路的主要长尾不在 I2S 播放，而在云端生成、TLS 建连和 TTS 首包。

## 已完成的板端优化

### VAD 句尾等待

句尾静默等待曾从 900 ms 调整为 650 ms，后续测试又使用了 500 ms。这样可以减少固定等待，但存在用户短暂停顿时提前截断的风险。日志中已经出现 500 ms 的结束判定，因此需要重点检查 ASR 最终文本是否被截短；不能只按延迟最小化处理。

### 延迟打点与串口处理

增加了九个阶段的统一时间戳，并把 `LAT` 输出延迟到一轮 TTS 播放完成后，避免串口打印阻塞网络收包、TTS 回调和 I2S 播放。这样可以分别看到 LLM 生成、TTS 建连、TTS 首包和本地播放的耗时，而不是只得到一个总时间。

### DeepSeek 请求和回答长度

- DeepSeek 改为 SSE 增量接收，关闭思考模式。
- 直接模式的 `max_tokens` 调整到 80，并使用 answer-only JSON，动作改由板端本地推断。
- 对话上下文由最多 3 轮进一步压到最近 2 轮，减少请求体、上传和模型前缀处理时间。
- 系统提示词在 LLM 对象初始化时拼装一次，但 DeepSeek 是无状态接口，所以完整系统提示词仍需随每次请求发送；这里只减少了板端重复拼接和临时字符串开销，并没有变成服务端会话缓存。

这些修改使部分会话的 `LLM_DONE` 明显早于旧版本，但无法消除 TTS 建连时间。

### SSE 答案解析与 TTS 队列

实现了增量解析 answer 字段、句子边界识别、答案队列和独立 FreeRTOS TTS 任务。JSON 动作和历史记录仍在完整答案后处理，避免动作解析失败影响已收到的文本。

但在当前板端直连实现中，为避免 DeepSeek TLS 和火山 TTS TLS 同时占用内部 RAM，TTS 任务要等 DeepSeek HTTP 流关闭后才真正释放。因此这部分已经改善了结构和容错，但没有形成真正的“LLM 生成期间并行 TTS”。

### TTS 播放完整性

- PCM 通过独立播放任务和有界队列交给 I2S，网络回调不直接阻塞播放。
- V3 双向 Session 必须收到明确的 `SessionFinished` 才判定完整。
- 记录 PCM 帧数、序号连续性和缺帧报警。
- I2S 写入失败会向 TTS 传播，不再把部分写入当成成功。
- 结束时向完整 DMA 环写入静音并检查结果，再关闭功放，避免最后几个字被立即静音截断。
- 已经收到部分 PCM 后不自动从头重播，避免网络失败时出现重复念话。

近期日志出现了如下完整性结果：

```text
TTS segment 1 END (... PCM bytes, ... frames, completion=explicit)
```

这部分主要改善稳定性和截断诊断，不会显著降低首音频延迟。

## V3 TTS 连接复用尝试

### 实现内容

在启动完成音频、唤醒模型和表情资源初始化后，板端尝试建立火山 TTS V3 双向连接；每轮只创建新的 Session，物理 WebSocket 保持复用，并增加心跳和自动重连。预期可以把后续轮次的 `TTS_CONNECTED` 降到接近 0。

### 实际结果

启动时确实出现过：

```text
TTS 2.0 WebSocket connected
TTS bidirectional connection is ready
TTS persistent connection warmup is ready
```

但第一次唤醒后马上打印：

```text
TTS reuse before cloud request: heap=55596, largest=44020
TTS persistent connection released before cloud request because internal heap is low
TTS persistent connection released
```

当前保护阈值为内部空闲堆至少 96 KiB、最大连续块至少 48 KiB。实测只有约 55 KiB 和 44 KiB，因此为保证 ASR/LLM TLS 不失败，常驻 TTS 被主动释放。后续日志仍反复出现新的 `TTS 2.0 WebSocket connected`，没有稳定出现 `TTS persistent connection reused`。

这说明连接复用逻辑本身已经实现，但 ESP32-S3 的内部 RAM 约束使它在当前固件和当前服务组合下无法稳定启用。

## 板载 TLS 内存限制

`ESP.getFreeHeap()` 和 `ESP.getMaxAllocHeap()` 统计的是内部 RAM，不是 PSRAM。PCM 队列和普通音频缓存可以放在 PSRAM，但 TLS 握手、mbedTLS 加密上下文、Wi-Fi 网络栈和部分 WebSocket 缓冲仍需要内部 RAM。

因此以下做法不能从根本上解决问题：

- 仅仅把 ASR、LLM、TTS 写成不同对象；它们仍共享同一内部堆。
- 仅仅增大 WebSocket 数据帧上限；这通常会增加缓冲占用。
- 仅仅把 PCM 队列移到 PSRAM；这只能释放音频缓存，不会迁移全部 TLS 内存。
- 盲目降低内存保护阈值；可能导致 ASR 或 DeepSeek 握手失败。

理论上可以在 ESP-IDF 中进一步配置 PSRAM、mbedTLS 动态缓冲和外部内存分配，但仍会有必须留在内部 RAM 的加密和网络内存，不能保证三个连接完全互不影响。

## 网关方案尝试

### 设计目标

网关在电脑或服务器上完成 DeepSeek SSE、火山 TTS 连接复用和首句流水线，ESP32-S3 只通过一个网关 WebSocket 接收文本、动作和 PCM。这样可以把 TLS 内存从板端移走，并让云端生成和 TTS 合成真正并行。

网关支持：

- DeepSeek 流式输出；
- 首个自然断句后触发火山 TTS；
- 火山 V3 双向 TTS 物理连接复用；
- 零 PCM 失败重试，部分 PCM 失败不重复播报；
- 令牌鉴权和可选 TLS 部署。

### 实际运行结果

曾在本机 PyCharm 环境启动网关，并将 ESP32 指向本机地址。但板端出现：

```text
Gateway warmup timed out; background reconnect remains active
Gateway connection timed out; using direct providers
```

随后 `LLM_FIRST_BYTE` 出现约 11 秒级耗时，说明板端等待网关连接超时后才回退到直连，体验反而变慢。问题不是电脑算力不足，而是网关启动时机、地址可达性、连接超时和回退策略叠加造成的。

网关不是必须和 ESP32 在同一 Wi-Fi 中，但服务器必须能被 ESP32 通过路由访问；跨网络时还需要公网地址、端口映射或反向代理，并应使用 TLS 和鉴权。部署复杂度、服务器常驻和网络依赖是它的主要成本。

当前已恢复为板端直连模式，网关代码保留但默认关闭。

## 当前听感结果

当前安全直连方案可以把短回答控制在一到两句，降低了 TTS 播放总时长和长回答截断概率，但说完后的首音频仍主要落在 **2 秒以上**。近期样本中最好约 **2.1 秒**，普通样本约 **2.3–2.7 秒**，网络或 TTS 抖动时可能超过 3 秒。

因此：

- **稳定低于 1 秒**：当前板端直连基本不可行，需要本地/边缘 ASR、Realtime/WebRTC 类链路或更强的云端流水线。
- **稳定 1.5 秒左右**：需要 TTS 连接复用和 LLM→TTS 真正重叠，同时解决内部 TLS 内存冲突。
- **稳定 2 秒内**：在网络稳定、回答很短、VAD 不误截断且常驻 TTS 真正可用时有机会，但当前日志还没有证明这一点。

## 后续建议

### 不部署网关、继续 Arduino 直连

1. 不要在启动阶段阻塞式预热 TTS。当前日志表明常驻连接刚建立就因内部 RAM 不足释放，预热只增加约 11 秒启动时间，没有带来后续收益。
2. 保留当前低内存保护和单次 TTS 回退，不要为了追求延迟盲目降低 96 KiB / 48 KiB 阈值。
3. 在相同网络和相同问题下连续测试至少 20 轮，统计 `AUDIO_UPLOAD_DONE → PLAYBACK_START` 的中位数和 P90。
4. 分别记录内部堆、PSRAM、`LLM_DONE → TTS_CONNECTED` 和 `TTS_REQUEST_SENT → TTS_FIRST_AUDIO`，确认瓶颈是内存、建连还是服务端首包。
5. VAD 继续使用 500 或 650 ms 前，先检查 ASR 是否经常截断；如果出现短暂停顿被截断，应退回 900 ms。

### 允许使用网关

1. 将网关部署到稳定运行的电脑、NAS 或云服务器，不依赖 PyCharm 临时窗口。
2. ESP32 使用服务器可达地址，不使用 `127.0.0.1`；跨网络时配置反向代理 TLS、鉴权和防火墙。
3. 网关连接失败必须快速失败并立即回退，不能让 ESP32 等待 10 秒以上才切换直连。
4. 通过网关日志同时测量 DeepSeek 首句、TTS 请求和首个 PCM，确认云端流水线确实重叠后再比较板端延迟。

### 迁移 ESP-IDF

ESP-IDF 值得考虑的原因是可以更细地控制任务、事件循环、mbedTLS 缓冲和 PSRAM 分配；但迁移本身不是延迟优化的充分条件。应先完成内存画像，再决定是否投入迁移，目标应是解决连接共存和稳定性，而不是期待框架更换直接减少一秒以上延迟。

## 验证日志关键词

板端直连成功时重点观察：

```text
TTS reuse before cloud request: heap=..., largest=...
TTS persistent connection reused
TTS bidirectional segment 1 complete (... PCM bytes, ... frames)
```

资源不足或异常回退时可能出现：

```text
TTS persistent connection released before cloud request because internal heap is low
TTS persistent Session unavailable; using one-shot fallback
TTS socket closed without an explicit final frame ...
TTS PCM sequence gap ...
```

这些日志应与 `LAT` 行一起保存，不能只根据总耗时判断某项优化是否生效。






# 20 轮对话测试结果

## 测试目的与条件

测试日期为 2026-09-19。本轮在关闭网关、关闭启动阶段 TTS 常驻连接、恢复 ESP32-S3 板端直连后进行，主要目的如下：

- 用 `VAD_END -> PLAYBACK_START` 直接测量“用户说完话 -> 扬声器开始播放”的听感等待时间；
- 确认 ASR、DeepSeek 和 TTS 的 TLS 内存开销，以及连接关闭后内存是否归还；
- 区分 TTS 截断发生在服务端/网络接收、板端 PCM 队列还是 I2S 播放阶段；
- 测量 TTS 工作任务的实际栈余量和 PCM 队列压力；
- 找出 WakeNet 已就绪后，`Desk-Emoji is Ready` 仍延迟多秒的具体原因。

|项目|配置|

## 本轮新增的诊断修改

### 说完时刻与阶段延迟

在原有延迟轨迹中增加 `VAD_END`。它记录本地 VAD 判定用户结束说话的时刻，因此不再使用包含用户说话时长的 `VAD_START`，也不再使用稍晚于句尾的 `AUDIO_UPLOAD_DONE` 估算听感等待。

本轮采用：

```text
说完后等待 = PLAYBACK_START - VAD_END
```

### ASR、LLM 和 TTS 内存快照

为三条云端链路补充了统一内存画像：

- `MEM ASR`：记录 `beginSSL` 前后、连接完成、麦克风缓冲分配/释放、最终结果和断开前后；
- `MEM LLM`：记录 `HTTP begin`、`POST` 和 `http.end()` 前后；
- `MEM TTS`：记录 TTS 连接、播放资源分配和断开前后；
- 除当前空闲量和最大连续块外，同时记录 `heap_min`、`internal_min`、DMA 内存和 PSRAM；
- TTS 文本缓冲会打印实际分配池，本次 20 轮均为 `pool=PSRAM`。

这些日志用于判断问题是总内存不足、最大连续块不足、内存泄漏，还是只能顺序复用 TLS 内存。

### TTS 完整性与资源压力

新增以下检查：

- 统计从服务端接收并成功排队的 PCM 字节数和块数；
- 统计实际写入 I2S 的 PCM 字节数和块数；
- 统计丢弃的 PCM、队列峰值和队列容量；
- 区分 PCM 缓冲来自 PSRAM 还是内部 RAM；
- 记录 TTS 帧数、PCM 时长、结束方式、序号末值和序号缺口；
- 记录 `TtsSentenceTask` 和 `TtsPlaybackTask` 的栈高水位；
- 零 PCM 重试退避从 500 ms 缩短为 150 ms；
- 对零 PCM、部分 PCM、明确完成帧和 socket 关闭分别输出日志。

### 启动动画耗时

为 `emoji_init()` 的 `eye_sleep`、`eye_wakeup`、`eye_center` 和 `eye_blink` 分别增加耗时日志，用来确认唤醒模型已经就绪后，主循环为什么仍迟迟没有进入可交互状态。

## 正常轮次耗时分解

排除第 7、19 轮 TTS 异常后，18 个正常样本的平均耗时如下：

|阶段|平均耗时|占说完后等待的比例|
|---|---|---|
|`VAD_END -> ASR_FINAL`|0.225 秒|约 9%|
|`ASR_FINAL -> LLM_DONE`|1.125 秒|约 46%|
|`LLM_DONE -> PLAYBACK_START`|1.098 秒|约 45%|
|合计|2.448 秒|100%|

其中 TTS WebSocket 建连通常约 0.66～0.77 秒；正常情况下，请求发出后到首 PCM 约 0.27～0.41 秒。因此 TTS 阶段约 1.10 秒不是 I2S 播放造成的，而是 TLS/WebSocket 建连与服务端生成首包的固定成本。

在当前板端顺序执行模型下，即使去除诊断日志的少量开销，也难以仅靠局部代码优化稳定节省约 0.45 秒并进入 2 秒以内。稳定 1.5 秒更不现实，除非实现连接复用、链路重叠、更快的服务端或本地推理。

## TTS 截断分析

### 板端播放链路没有丢数据

所有成功接收 PCM 的轮次均满足：

```text
queued == played
discarded == 0
failed == 0
```

队列峰值最高为 `19/48`，全部 PCM 缓冲来自 PSRAM，内部 RAM 分配为 0。这说明：

- 播放队列没有溢出；
- PSRAM 分配成功；
- 网络回调接收的 PCM 全部交给了 I2S；
- 滑动串口监视器不是本轮 TTS 截断的直接原因；
- 如果听到回答突然结束，缺失数据发生在进入板端播放队列之前。

### 上游连接存在无完成标志关闭

20 轮中有 16 轮收到明确结束标志，另外 4 轮以 `socket-close` 结束：

|轮次|PCM 字节|音频时长|判断|
|---|---|---|---|
|6|104448|6.528 秒|可能已经完整，但缺少协议完成标志|
|7|24576|1.536 秒|明确截断，不可能覆盖完整回答|
|10|51200|3.200 秒|相比相近长度回答明显偏短，高度可疑|
|13|59392|3.712 秒|相比相近长度回答明显偏短，高度可疑|

当前单向接口兼容了“服务端用关闭 socket 表示正常结束”的情况，所以代码只要收到过 PCM，就会在无明确结束帧的关闭后继续排空音频并判定成功。这能避免把正常关闭误判为失败，但也会把第 7 轮这种部分音频误判成完整。

所有轮次的 `seq_last=0` 表明本次单向服务响应没有提供可用 PCM 序号，因此 `gap=0` 只代表没有检测到序号跳变，不能证明音频完整。

第 19 轮第一次连接成功后收到 0 PCM 并断开。新增的 150 ms 快速重试生效，第二次成功收到 `106200` 字节、6.637 秒 PCM 和明确完成标志。相较原来的 500 ms 退避，异常路径减少了 350 ms 固定等待。

### 当前不能直接重试部分音频

第 7、10、13 轮已经向扬声器播放了部分回答。如果直接从头重试，会让用户再次听到已经播放的开头，因此现有逻辑只对 0 PCM 失败重试。这是为了避免重复播报，但代价是部分 PCM 截断无法自动恢复。

更可靠的后续方案是：DeepSeek HTTP 完全关闭后，再按轮建立火山 V3 双向连接，以明确的 `SessionFinished` 作为完成条件；连接只在本轮 TTS 使用，播放后关闭，不在 ASR/LLM 阶段常驻，也不使用网关。该方案重点改善完整性，不承诺降低首音频延迟。

## 内存与 TLS 结论

### TLS 内存主要来自内部 RAM

|阶段|连接前内部空闲|连接后内部空闲|约占用|
|---|---|---|---|
|ASR TLS|约 99.6 KiB|约 54.5 KiB|约 45 KiB|
|DeepSeek HTTP/TLS|约 86.7 KiB|约 41.0 KiB|约 45 KiB|
|TTS TLS|约 86.1 KiB|约 40.9 KiB|约 45 KiB|

TTS 建连并创建播放资源后，内部空闲最低约 36.2 KiB；整个 20 轮测试记录到的 `internal_min` 最低约 33.5 KiB。PSRAM 始终还有约 5.17 MiB，但 TLS 上下文和网络缓冲仍主要消耗内部 RAM。

最大连续内部块也会在 TLS 工作时下降：

- 空闲、连接前通常约 45 KiB；
- ASR 连接后通常约 28 KiB；
- TTS 连接和播放资源就绪后通常约 16 KiB；
- 断开后重新恢复到约 45 KiB。

因此，当前固件可以顺序运行 ASR、LLM 和 TTS，但不适合让第二条 TLS 连接与现有连接同时常驻。TTS 常驻后剩余总量和最大连续块都不足以可靠建立下一条 ASR/LLM TLS。

### 未发现持续内存泄漏

测试初期内部堆约 101.5 KiB，进入稳定对话后每轮开始前约 99.8 KiB；后半段没有继续下降。PSRAM 从约 5.181 MiB 下降到约 5.178 MiB 后也保持稳定。结合每次 `http.end()` 和 WebSocket `disconnect()` 后的回升，可以判断：

- TLS 内存基本能够归还；
- 没有随对话轮数持续增长的明显泄漏；
- 初期几 KiB 变化更像历史记录、字符串容量和网络库一次性缓存稳定下来后的结果；
- 当前主要问题是同一时刻可用的内部 RAM 和最大连续块，而不是 PSRAM 总量或每轮泄漏。

### 任务栈和队列不是当前瓶颈

FreeRTOS 的高水位表示任务生命周期内“最少剩余栈”，不是已经使用的栈：

|任务|配置栈|最少剩余|估算最大使用|
|---|---|---|---|
|`TtsSentenceTask`|8192|4352～4580|约 3.6～3.8 KiB|
|`TtsPlaybackTask`|4096|正常轮次 2120|约 2.0 KiB|

理论上可以把两个任务栈分别调整到约 6144 和 3072，合计释放约 3 KiB 内部 RAM。但这远小于另一条 TLS 所需的约 45 KiB，不能解决常驻连接或并发 TLS，反而会减少错误路径的安全余量。因此当前不建议为了延迟缩减任务栈。

## 启动动画与唤醒体验

新增日志确认，WakeNet 初始化完成后到 `Desk-Emoji is Ready` 的主要阻塞来自 OLED 启动动画：

|步骤|耗时|
|---|---|
|首次 `eye_sleep`，由总时间反推|约 3.473 秒|
|`eye_wakeup`|5.431 秒|
|`eye_center`|0.323 秒|
|`eye_blink`|2.398 秒|
|`emoji_init()` 总计|11.625 秒|

`eye_wakeup` 和 `eye_blink` 会反复调用 `oled.display()`，单次全屏 I2C 刷新约需 0.30～0.34 秒。WakeNet 虽然已打印 Ready，但主循环必须等阻塞式 `emoji_init()` 返回后才能真正处理唤醒事件。因此开机后的这 11.6 秒会表现为唤醒词不灵敏或完全没反应，但这不是 WakeNet 模型阈值造成的。

本轮只有已经成功检测到的唤醒事件，日志无法统计用户说了但没有触发的次数，所以不能仅凭本日志判断设备进入主循环后的真实漏唤醒率。

第 19 轮 ASR WebSocket 建连耗时约 2.7 秒，明显高于其他轮次的约 0.6～0.74 秒，但它发生在用户开始说话前，属于网络建连长尾，会影响“唤醒后多久开始听”，不影响本节使用的“说完后等待”统计。

## 本轮最终结论

1. 板端直连正常轮次的说完后等待平均约 2.448 秒，中位数约 2.512 秒，可以稳定在 2.1～2.7 秒，但尚未达到稳定 2 秒内。
2. 正常延迟几乎由 DeepSeek 和 TTS 平分；I2S 提交本身只有亚毫秒级，不是延迟瓶颈。
3. PCM 队列、PSRAM 和 I2S 没有丢数据，机器人偶发说话截断来自 TTS 服务端或 WebSocket 在完整音频到达前关闭。
4. 0 PCM 快速重试已经有效，但部分 PCM 不能直接从头重试，否则会重复播报。
5. TLS 内存会在连接关闭后归还，20 轮没有显示持续泄漏；真正限制是约 45 KiB/连接的内部 RAM 和连续块需求。
6. 当前内存条件不支持在 ASR/LLM 期间保留 TTS 常驻 TLS。缩减约 3 KiB 任务栈不能改变这个结论。
7. 启动阶段约 11.6 秒的不可交互时间来自阻塞式 OLED 动画，需要独立优化，不能归因于唤醒模型。

## 基于本轮结果的后续建议

1. 保持不用网关，也不恢复跨轮 TTS 常驻连接。
2. 优先把 TTS 改为 DeepSeek 释放 TLS 后建立的“单轮 V3 双向连接”，使用明确 `SessionFinished` 判断完整性，完成后立即关闭。
3. 明确设置 OLED I2C 高速时钟，并把启动动画改为极少数刷新或非阻塞动画；旧动画保留在 `#if 0` 中。
4. 本轮诊断完成后，用编译开关关闭高频 `MEM`、`STACK` 和 `TTS PLAYBACK` 日志，保留 `LAT`、零 PCM、部分 PCM 和无明确结束帧告警，再重新测量正式版本延迟。
5. 暂不缩减 TTS 任务栈和队列；它们有足够余量，也不是截断或延迟来源。
6. 如果后续仍要求稳定 2 秒内，需要从更快的模型/区域、TLS 会话复用、可并发的内存布局或本地推理中取得至少约 0.45 秒收益，仅调整回答长度和串口日志不足以稳定达到目标。
